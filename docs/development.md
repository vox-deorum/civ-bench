# Developer guide

This guide is for people **changing** `civ-bench`: adding an analysis, wiring in a new estimator, extending the config schema, or understanding how a run executes. If you only want to *use* the harness, the [Getting Started guide](getting-started.md) and the [Configuration guide](configuration.md) are what you want.

> The canonical rulebook is **[AGENTS.md](../AGENTS.md)**. It states the invariants every change must hold and the conventions for the repo. This guide is the practical, narrative companion: read AGENTS.md for the rules, read this for how to apply them.

---

## The three invariants

Every change is measured against these. A change that violates one is wrong even if it "works":

1. **Config over code.** Anything that varies between datasets, experiments, or model line-ups lives in JSON under [configs/](../configs/), never hardcoded. Adding a model or experiment must require zero Python edits.
2. **Modular and pluggable.** Each analysis is a self-contained unit behind a common interface and a registry. Adding one is one module plus one registry entry plus one config block, touching nothing else. Robustness variants of an existing analysis (bootstrap CIs, identity groupings) are *params on the parent module*, not new modules.
3. **Reports are generated, never authored.** Analyses return data; the report layer renders it. No notebook is the source of truth. If a result cannot be regenerated by `civ-bench run`, it does not belong in the repo.

## Repository and package map

The installable package is `bench/`. Each subpackage owns one stage kind or one shared concern:

| Path | Responsibility |
|------|----------------|
| `bench/cli.py` | The `civ-bench extract\|run\|report` entrypoint. |
| `bench/config/` | Load and validate JSON into typed config objects; resolve the output root and the DAG edges once, at load time. |
| `bench/pipeline/` | The DAG builder and scheduler: resolve `needs` and `uses`, topo-sort, run stages. |
| `bench/extract/` | Game SQLite DBs to canonical CSVs; composes the orthodox `player_type`. |
| `bench/data/` | Canonical CSV loading and the shared filter resolver (`apply_filter_spec`). |
| `bench/catalog/` | The model and experiment catalogs, backed by `configs/*.json`. |
| `bench/estimators/` | Victory-probability predictor producers: tune, train, load, infer. |
| `bench/adjust/` | Derived-table producers (the `strength` panel). |
| `bench/analyses/` | The pluggable analysis modules, in five families. |
| `bench/stats/` | The statistics layer: OLS/logistic wrappers, clustered/weighted fits, heatmaps. |
| `bench/reports/` | Assemble analysis artifacts into Markdown and HTML. |
| `bench/plotting/` | Shared styles, colors, and figure helpers. |

Tests live in `tests/` at the repo root, one file per area. The roadmap and the staged build history live in `plans/`.

## Conventions that matter

- **It is a package, not loose scripts.** Use absolute imports from `bench.*`. Commands run from the repo root via the CLI, never `cd models && python compare.py`.
- **Analyses return data, not side effects.** A module produces an `AnalysisResult` (tables, figures, a summary). Writing files and printing is the runner's and report layer's job. This is what makes a module reusable from a test or a notebook.
- **Estimators are producers, not analyses.** Training, tuning, saving, loading, and inference live under `bench/estimators/`. An estimator exposes one artifact, a `predictions.csv`. Scoring that artifact is a separate `prediction.*` analysis.
- **`adjust` stages are derived-table producers.** The strength-panel derivation lives in `bench/adjust/strength.py` once, not duplicated inside each rating. That duplication was a real bug in the old repo, and removing it is the point of the stage.
- **Determinism.** Same config plus same `runs/` data must give byte-stable tables. Thread the top-level `seed` into anything random; never call an unseeded RNG. Rendering carries no timestamps.
- **All dependencies are mandatory.** No `try/except ImportError` soft-fail. Import torch, xgboost, optuna, and call Rscript directly. A missing dependency is a loud hard error with an install hint, never a silently skipped stage. The import-light config layer stays free of heavy imports; the registry that pulls matplotlib/statsmodels/Rscript is imported only on the run path.
- **JSON is the source of truth and is validated on load.** Unknown keys and missing required fields are hard errors. When you add or rename anything the run-spec can select, update [configs/benchmark.md](../configs/benchmark.md) in the same change.

## How a run executes

1. `load_config` reads the run-spec, validates it (unknown keys, required fields, registry membership, filter and grouping resolution, and so on), and resolves the stage graph once.
2. `build_dag` turns the kind ordering, the explicit `needs`, and the referential `uses` edges into a single topological order.
3. The CLI resolves `--only` / `--skip` into the subset to run, then executes each stage in topo order. Each stage kind has a runner (`run_extract`, `run_estimator`, `run_adjust`, `run_analysis`, `run_report`).
4. Each analysis persists a `result.json` plus its tables and figures under the resolved output root. The report stage reads those manifests, which is why `civ-bench report` reproduces the document from disk without recomputation.

The dry-run printer (`--dry-run` or `--skip all`) shares the exact same resolved graph as the runner, so what it prints is what would run.

## Adding an analysis module

This is the most common extension. An analysis implements one small interface and registers under a string name so JSON can select it.

The interface, from [bench/analyses/base.py](../bench/analyses/base.py):

```python
class Analysis(ABC):
    module: str = ""                       # the registry key used in the run-spec
    default_all_estimators: bool = False   # True: empty uses.estimators means "all enabled"

    def run(self, ctx: AnalysisContext) -> AnalysisResult: ...
```

The `AnalysisContext` hands you everything resolved (config, catalog, output-rooted paths) so you never re-derive paths or re-implement filtering:

- `ctx.load_table("strength")` reads a canonical table or an adjust stage's output by name.
- `ctx.load_predictions("attention")` reads an estimator's `predictions.csv`.
- `ctx.apply_filter(df)` applies the global `data.filter` narrowed by this stage's `filter`, using the same semantics the config validated.
- `ctx.params` is this stage's `params` block; `ctx.uses_estimators()` / `ctx.uses_tables()` resolve the `uses` references.

You return an `AnalysisResult`: `tables` (a dict of named DataFrames), `figures` (a dict of named matplotlib figures), a `summary` string, and optional `metadata`. A module that legitimately produces nothing (for example `calibration.cell_baseline` on a fully uncontrolled run) returns an empty result, and `is_empty()` lets the runner record it without error.

A minimal real module, [exploratory/model_token_costs.py](../bench/analyses/exploratory/model_token_costs.py):

```python
from ..base import Analysis, AnalysisContext, AnalysisResult

class ExploratoryModelTokenCosts(Analysis):
    module = "exploratory.model_token_costs"

    def run(self, ctx: AnalysisContext) -> AnalysisResult:
        tokens = ctx.apply_filter(ctx.load_table("tokens"))
        pricing = ctx.catalog.pricing_per_million()
        # ... compute per-row cost, aggregate ...
        return AnalysisResult(tables={"token_costs": table}, summary="...")
```

The steps to add one:

1. **Write the module** under the right family directory (`bench/analyses/<family>/`), subclassing `Analysis` and setting `module` to its registry name (for example `performance.my_view`). Do the work in `run`, return an `AnalysisResult`.
2. **Register it** in [bench/analyses/registry.py](../bench/analyses/registry.py) by adding the name-to-class entry (and export it from the family `__init__`).
3. **Declare it in the schema** so the config validates: add the module name to `bench.config.schema.ANALYSIS_MODULES`. (A name listed in the schema but absent from the registry is treated as a reserved, not-yet-implemented optional module and fails loud with a clear message if selected.)
4. **Document it** in [configs/benchmark.md](../configs/benchmark.md) section 6.2 with its params, and add it to a template (enabled in core, or `enabled: false` in the full template if it is optional).
5. **Test it** in `tests/test_analyses.py` against a small synthetic fixture.

If your idea is a variant of an existing analysis (a different grouping, confidence intervals, a different reference), it is almost certainly a **param on the existing module**, not a new module. That is invariant 2.

## Adding an estimator

Estimators live under [bench/estimators/](../bench/estimators/). A predictor subclasses `BasePredictor` (or a torch base) and is mapped from a string id in [bench/estimators/registry.py](../bench/estimators/registry.py):

```python
MODEL_REGISTRY: Dict[str, Type[BasePredictor]] = {
    "naive": NaivePredictor,
    "score": ScorePredictor,
    # ...
    "attention_mlp": AttentionMLPPredictor,
}
```

To add one:

1. Implement the predictor class under `bench/estimators/models/` following an existing model (fit, predict, save/load state via `metadata.json`).
2. Add its id to `MODEL_REGISTRY`.
3. Add the id to the `prediction_models` list in [configs/models.json](../configs/models.json) (with a color and `predict_order`), so an estimator entry's `model` can select it.
4. Add a test in `tests/test_estimators.py`.

The two axes (`fit` and `predict`) and saving/loading are handled by the shared estimator runner, so a new model only implements the math. `load_model` dispatches on the saved `metadata.model_class`, which is how `fit: pretrained` resolves the class.

## Adding an `adjust` module

`adjust` modules are derived-table producers under [bench/adjust/](../bench/adjust/), mapped by name in `bench/adjust/registry.py` (today only `strength`). A module consumes an estimator's predictions and emits a named table that downstream stages reference via `uses.tables`. Follow the `strength` module's shape: read the referenced estimator's predictions, compute the derived table, write it plus its always-on audit CSVs, and return a result describing what it wrote. Register the name and document the params and table columns in [configs/benchmark.md](../configs/benchmark.md) section 5.

## Extending the config schema

The config layer in [bench/config/](../bench/config/) is intentionally import-light (no torch, no matplotlib) so validation is fast and dependency-free. When you add a selectable thing:

- Add it to the relevant registry list in `bench.config.schema`.
- Add or extend the validation rule in the same change (unknown keys, required fields, type checks, reference resolution).
- Mirror it in [configs/benchmark.md](../configs/benchmark.md) and, if it is a new validation, in `tests/test_config.py`.

The whole numbered validation contract is benchmark.md section 8; keep it in parity with the code.

## Running the tests

```bash
pip install -e ".[test]"
pytest
```

The suite (in [tests/](../tests/), one file per area) exercises config validation, DAG resolution, catalog logic, and the analysis modules against small synthetic fixtures. Tests must **not** touch machine-specific data roots or run stages against real `runs/` data. When you add a module or a validation rule, add or extend its test in the same change.
